# 多Agent协作工作流

> **本文定位（协作约定文档，非自动执行引擎）**：本文件是**多 Agent 协作的流程约定与调用顺序说明**，供主 Agent（或人类）按阶段手动编排。本仓库通过 `Task` 工具 + 子 agent 文件基名（如 `architecture-designer`）派发子任务；本文件不自带调度能力，请按"各阶段详细说明 / 完整工作流示例"逐阶段触发对应 agent。
>
> **本项目边界（shop-agent）**：主栈 Python/FastAPI + Rust(order-service, axum/sqlx)，无 Java 服务、当前无前端目录。因此 `java-coder`/`frontend-coder` 仅作通用参考，**仅当仓库出现 `.java` / `.vue`/`.tsx` 等文件时才调用**；Rust 编码由 `python-coder` 协调或遵循 `rust-code` rule，必要时人工落地。所有 LLM/Agent 代码须遵循 `llm-agent` rule（网关出口、Prompt 注入三道防线、人在回路）。

## 设计哲学与已知限制

> **本工作流不承诺 100% 让最终产物符合期望。** 这是 Agent 系统的底层逻辑限制，而非实现缺陷。下面把限制说清，也说明本工作流用哪些机制把"不符合期望"的概率压到极低（而非清零）。

### 四类根本限制（无法根除）

1. **目标定义本身模糊**：用户的"期望"常含未言明的约束（预算、风格、优先级、隐性偏好）。Workflow 只能逼近*显式*目标，读不到没写出来的隐性偏好。
2. **每步信息损失与误差累积**：串行传递中间结果，每步 LLM 输出具概率性、工具调用有误差。微小偏差经 3~5 步叠加后分布可能偏离初始期望（误差传播）。本工作流只降低单步方差，无法消除方差。
3. **外部环境/工具不可控**：依赖搜索、数据库、API 等外部资源；若其返回偏见/过期/异常，产物可能建立在错误事实上。验证步骤本身也可能因幻觉误判。
4. **"符合期望"是主观判断**：同一产物不同人/不同时刻标准不同。Workflow 只能按预设质量指标自校验，最终符合与否由人裁定。

### 本工作流用什么机制缓解（把概率压低，非清零）

- **目标澄清（阶段0）**：首步先反问用户确认关键约束，形成结构化 `scope.md`，后续阶段不得超出。
- **分阶段验证**：每阶段产出后做一致性/反思检查；审查阶段对低置信度结果触发回退或人工介入。
- **可追溯**：每阶段中间产物落盘到 `.codebuddy/run/{task}/` 并展示给用户，允许过程中纠偏。
- **回退与人工介入**：超阈值或循环超限即停并报告偏离点，不盲目继续。
- **多路径投票（可选）**：高不确定任务可并行多条推理链择优/合并（见扩展工作流）。

> 这些手段是用更多控制逻辑与计算换取鲁棒性，但**不突破上述四类限制**。执行者须对最终产物保持人工终审。

## 各阶段详细说明

### 阶段0：目标澄清（必须，首要步骤）

> 对应设计哲学"目标澄清"机制。目的是把隐性期望显性化，避免后续阶段在错误假设上发散。

#### 任务
1. **反问用户确认关键约束**（不要跳过）：预算/工期、目标风格或优先级、性能/安全/合规硬指标、明确"不做项"（out-of-scope）。
2. 将模糊需求拆为结构化条目，形成 `scope.md`。
3. 若用户拒绝澄清或信息确实缺失，记录"未确认假设"并在 `scope.md` 标注，后续阶段按假设推进但须显式提示风险。

#### 输出
- `scope.md`（落盘到 `.codebuddy/run/{task}/scope.md`），至少包含：
  - **目标**：一句话可验证的结果描述
  - **验收清单**：可逐项勾选的交付标准
  - **范围边界**：明确不做的事
  - **关键约束**：技术栈/性能/合规/预算等硬限制
  - **未确认假设**：本次推进所依赖但未核实的前提

#### 硬约束
- **后续所有阶段（架构/编码/审查/测试）的输入必须引用 `scope.md`，不得超出其范围边界**；如发现范围需扩大，返回本阶段重新澄清，而非自行扩写。

#### 特例：依据既有设计文档落地（如 platform-engineering 系列）

> 当任务目标是"依据仓库已有架构文档做实现"而非"从零设计"时，阶段0 的 `scope.md` 须额外锚定文档，避免 agent 重新发明已定的架构。

- **设计依据**：在 `scope.md` 写明所依据的文档路径与篇目（如 `docs/platform-engineering/01-LLM流量网关设计.md`），并标注该文档状态（已定稿 / 目录大纲骨架）。
- **权威声明**：相关架构决策以该文档为唯一权威；编码/架构阶段 agent **必须先 `read_file` 对应篇目再动手**，禁止新建与之冲突的方案。
- **范围收窄**：只做"实现与衔接"，不重新论证架构（除非文档明确标为"待补/大纲"且用户要求补全）。
- **文档未覆盖处**：在 `scope.md` 的"未确认假设"中记录"按 `apps/` 现有代码惯例处理"，审查时由 `code-reviewer` 核对是否偏离文档既定决策。
- **跨篇依赖**：若目标篇目依赖其他篇（如 01 依赖 02/03/06/10），须将依赖篇目一并列入 `scope.md` 的"设计依据"，按顺序落地，不并行启动有依赖的篇目。

### 阶段1：架构设计 (architecture-designer) —— 条件触发，默认跳过

> **本项目默认先完成架构设计并经人工评审（落地于 `docs/architecture/*.md`），再进入编码。因此本阶段通常为"跳过"，仅当无现成设计文档时触发。**
>
> **自动化设计门禁（hooks 驱动）**：触发 fresh 设计（`architecture-designer` 从零产出 `design.md`）后，编排**不会自动进编码**，而是拉起"设计门禁"——要求人工 review `design.md` 并运行 `python scripts/orchestrator_hook.py approve --task <task>` 放行，编码阶段才解锁。若依据既有文档跳过本阶段，则无门禁，直进编码。门禁属纯 hook 层，不污染领域状态机（eval 自动批准）。详见 `agent_driver.md` 的"设计门禁（方案 A）"与"scope.md 质量锚点（方案 C）"。

#### 触发条件（满足任一才执行，否则跳过直接进入阶段2）
- 任务目标是从零设计新系统，且 `docs/architecture/` 中无对应 design/implementation-plan 文档；
- 或既有设计文档明确标为"大纲/待补"且用户要求补全架构。

#### 跳过时的强制动作（依据既有设计文档落地）
- 直接进入阶段2，**编码/设计 agent 必须先 `read_file` `scope.md` 锚定的设计文档再动手**（联动上文"特例"机制，第 113-121 行）；
- 禁止新建与既有文档冲突的方案；只做实现与衔接。

#### 触发时的输入
- 业务需求文档
- 技术约束条件
- 现有系统架构信息
- 性能/安全/可用性要求

#### 触发时的任务
1. 分析业务需求和技术约束
2. 设计系统整体架构（分层/微服务/模块化）
3. 定义模块划分和职责边界
4. 设计API接口契约（请求/响应格式）
5. 数据库模型设计
6. 技术选型（框架、中间件、工具链）

#### 触发时的输出
- 架构设计文档（doc.md，建议落地 `docs/architecture/`）
- 模块划分图
- API接口定义
- 数据库ER图
- 技术栈清单

### 阶段4：代码审查 (code-reviewer)

#### 输入
- 源代码文件
- 架构设计文档
- 编码规范

#### 任务
1. **代码规范检查**
   - 命名规范（类名、方法名、变量名）
   - 代码格式（缩进、空格、换行）
   - 注释质量
   - 导入组织

2. **设计质量审查**
   - 单一职责原则
   - 开闭原则
   - 依赖倒置原则
   - 接口隔离原则

3. **代码坏味道识别**
   - 重复代码
   - 过长方法/类
   - 过多参数
   - 深层嵌套

4. **安全审查**
   - SQL注入风险
   - XSS漏洞
   - 敏感信息泄露
   - 权限控制缺失

5. **性能问题识别**
   - 数据库N+1查询
   - 不必要的对象创建
   - 低效的算法复杂度
   - 资源泄露

#### 输出
- 代码审查报告
- 问题分级列表（阻塞/警告/建议）
- 改进建议

#### 决策分支
```
审查结果
    │
    ├── 存在阻塞问题 ──► 返回编码Agent修复 ──► 重新审查
    │
    ├── 仅存在警告/建议 ──► 记录问题 ──► 继续下一阶段
    │
    └── 无问题 ──► 继续下一阶段
```

### 阶段5：测试生成 (test-generator)

#### 输入（规格驱动，非代码驱动）
- **首要输入**：阶段0 的 `scope.md` 验收清单 + 人审过的接口契约（OpenAPI / 接口模块 / `contract.py`）
- API接口定义（同属上述契约）
- 审查通过的源代码 —— **仅作"公开签名/符号寻址"参考（函数名、参数、类型、返回类型）**，**不得作为行为依据**（详见 `test-generator` 强约定）
- **编排要求（结构性保证"只给签名"）**：主代理在调用 test-generator 前，应先用 `python scripts/signature_view.py <模块路径>` 提取签名，将**该工具的输出**（而非实现文件原文）作为"代码签名"喂给 test-generator；实现文件原文不进入 test-generator 上下文。这把"不读实现"从意愿变成结构默认。

#### 任务
1. **代码分析**
   - 识别公共方法及其职责
   - 分析依赖关系
   - 确定边界条件和异常情况

2. **单元测试生成**
   - 正常场景测试
   - 异常场景测试
   - 边界条件测试

3. **集成测试生成**
   - 数据库交互测试
   - 外部API调用测试
   - 模块间协作测试

4. **端到端测试生成**（关键路径）
   - 主业务流程测试
   - 用户场景测试

5. **测试验证**
   - 运行测试确保通过
   - 检查覆盖率是否达标

#### 输出
- 单元测试代码
- 集成测试代码
- 端到端测试代码
- 测试报告
- 覆盖率统计

#### 自动生成测试的防假绿规范（必读）

测试由 Agent 自动生成时，最大失控风险不是"跑飞"，而是**假绿**：Agent 把断言改成自己理解的行为，代码与测试一起错，但 CI 全绿，使你失去"绿色"这个信号本身的可信度。按测试来源分三层处置：

| 层级 | 测试来源 | 审核节奏 | 防线 |
|------|---------|---------|------|
| 第1层 断言型 | **由确定性契约工具生成**（如 FastAPI 用 `schemathesis` 读人审过的 OpenAPI 文档、或 Spring Cloud Contract / Pact 从契约生成；机器翻译、非 LLM） | **免审**——审核点在契约定义时（人审）已发生，且翻译可复现无自由发挥 | 契约先行，机器生成只是确定性翻译；前提：红了只许改实现 + 契约定期审计 |
| 第2层 生成型 | Agent 自由编写（定义行为+断言） | **人扫方向 + 机器验实现**，非只审代码/只审描述 | 每个测试文件顶部 docstring 写 `Rule: <本文件验证的业务规则>`（人 30 秒扫方向）；机器把关实现：禁空断言/恒真断言（结构性扫描）+ 变异测试（注入缺陷测试必须失败）+ 沙箱隔离执行（证明测试在真实环境跑通而非仅在 dev 环境），证明测试真在验证东西 |
| 第3层 CI 回路 | 阶段6 自动修复补的测试 | **说不出依据即拒绝 + 实现/测试分离** | 修复 PR 须附"修复前失败用例 → 修复后状态"（红绿证据），否则打 `needs-human`；改已有测试须声明类别并附契约/需求变更依据走人审，不得自行改断言消红 |

**铁律**：第2/3 层测试文件**禁止**以 `assert True`、`pass`、或注释掉失败断言的方式通过；code-reviewer 与 CI 回路须把此类"伪通过"视为 `[BLOCKING]`。覆盖率数字**不是**合格担保物（弱断言也能刷满），机器验证（注入缺陷测试必失败 + 沙箱隔离执行）才是。

#### 覆盖率要求
> 与 CI 门禁对齐：`.github/workflows/ci-tests.yml` 中 `COVERAGE_GATE = 60`（总体覆盖率）。

| 测试类型 | 目标覆盖率 |
|----------|-----------|
| 总体覆盖率（CI 门禁） | ≥60% |
| 单元测试 | ≥60% |
| 集成测试 | ≥40% |

## LLM/Agent 专项治理（本项目强制）

> shop-agent 是多 Agent 平台，涉及 LLM 调用与工具编排。**以下环节不可省略**，细节见 `llm-agent` rule 与 `docs/platform-engineering/` 系列。

### 1. 网关出口（架构/编码阶段）
- 所有 LLM 调用经 `gateway`（唯一出口），业务代码 `base_url` 指向 `LLM_GATEWAY_URL`，禁止直连供应商。
- 涉及 Agent 编排时，工具调用结果视为不可信外部输入，使用前校验。

### 2. Prompt 注入三道防线（编码/审查阶段）
- 输入侧、输出侧、工具参数侧三道检测卡在网关；业务不在本地重做检测逻辑。
- `code-reviewer` 审查 LLM/Agent 代码时，须核对是否依赖网关检测、是否误把外部内容拼进 system prompt。

### 3. 人在回路（编码/审查阶段）
- 涉及资金/不可逆操作（退款确认、退货审核）必须卡人工审批节点，状态用显式枚举（如 `PENDING_HUMAN_APPROVAL`）。
- `code-reviewer` 须确认高风险动作未被自动放行。

### 4. 可观测与缓存（测试/交付阶段）
- LLM 调用处记录 token 用量、延迟、命中缓存与否；指标接入 Prometheus。
- 重复/相似 prompt 优先走网关语义缓存，业务侧缓存仅用于非 LLM 数据。

## 流程中断预防机制

### 0. 可追溯产物路径约定（贯穿全流程）

> 对应设计哲学"可追溯"机制。所有阶段的中间产物必须落盘，供下游读取与用户中途纠偏，避免"信息在对话里丢失、下游凭空想象"导致的偏离。

- **统一目录**：`.codebuddy/run/{task}/`，`{task}` 为本次任务的简短标识（如 `user-mgmt`）。
- **落盘要求**：阶段0 产出 `scope.md`；架构设计产出 `architecture.md`；数据库设计产出 `db-design.md` + 迁移脚本；API 设计产出 `api-design.md`；每阶段审查/验证产出 `*.review.md`。
- **下游约束**：下一阶段 agent 启动时必须 `read_file` 对应上游产物路径，不得仅凭口头摘要推进。
- **用户纠偏**：每个阶段产物产出后展示给用户，用户可在中途要求调整方向，调整后回填 `scope.md` 的"未确认假设/范围边界"。

### 1. 分阶段验证总要求

> 对应设计哲学"分阶段验证"机制。每个子任务完成后，除自身产出外，须做一次**一致性/反思检查**（可用独立 Prompt 或对照 `scope.md` 验收清单），确认未偏离阶段0 约定的范围与约束。低置信度（如关键决策无依据、与 `scope.md` 冲突）必须触发回退或人工介入，禁止带病进入下一阶段。

### 预防策略

#### 1. 需求阶段预检
```
用户输入需求
    │
    ▼
┌─────────────────┐
│ 需求完整性检查   │── 缺失必填项？──► 立即提示补充
│ (自动校验)      │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 技术可行性预检   │── 技术栈冲突？──► 提前给出替代方案
│ (基于知识库)    │
└────────┬────────┘
         │
         ▼
    进入架构设计
```

#### 2. 架构设计阶段输出标准化
架构设计文档必须包含：
- [ ] 明确的模块边界（减少编码歧义）
- [ ] 详细的接口契约（Request/Response示例）
- [ ] 数据库变更脚本（与本项目技术栈匹配：sqlx/Alembic，不套用 Flyway 格式）
- [ ] 异常处理策略
- [ ] 技术选型理由（避免后续质疑）

#### 3. 编码阶段自检机制
编码Agent提交前自动执行：
- **编译/类型检查**：确保代码可编译（Rust `cargo check`、Python `mypy`/ruff）
- **单元测试**：基础路径覆盖
- **代码规范**：Linter自动检查
- **安全扫描**：基础规则检查（含 SQL 注入、Prompt 注入初筛）
- **架构对齐**：与设计方案对比

自检不通过 → 自动修复（最多2次）→ 仍失败才提交审查

#### 4. 代码审查分级策略
```
┌─────────────────────────────────────────┐
│           代码审查流水线                 │
├─────────────────────────────────────────┤
│  第一层：自动化检查（秒级）               │
│  - Linter、静态分析、安全扫描            │
│  - 自动修复可修复问题                     │
├─────────────────────────────────────────┤
│  第二层：AI快速审查（分钟级）             │
│  - 仅标记阻塞级问题                       │
│  - 警告级问题记录但不中断                 │
├─────────────────────────────────────────┤
│  第三层：深度审查（需要时触发）            │
│  - 复杂业务场景分析                       │
│  - 性能瓶颈识别                          │
└─────────────────────────────────────────┘
```

**阻塞问题预判与规避**：
| 阻塞问题 | 编码阶段规避措施 |
|---------|----------------|
| SQL注入 | 强制参数化查询（sqlx `.bind()`/`$N`、SQLAlchemy/ORM 绑定参数），禁用字符串拼接 SQL |
| 空值/缺省风险 | 显式处理 Option/None 与默认值，空值检查自动化 |
| Prompt 注入 | 用户内容一律经 LLM 网关三道检测，业务不重做检测（见 `llm-agent` rule） |
| 魔法数字 | 常量提取检查，未提取则警告 |
| 长方法 | 方法行数限制（>50行警告，>100行阻塞） |

### 快速修复机制

| 场景 | 自动修复 | 重试次数 | 仍失败处理 |
|------|---------|---------|-----------|
| 编码自检失败 | 自动修复常见问题 | 2次 | 标记后提交审查 |
| 审查阻塞问题 | 编码Agent按建议修复 | 3次 | 人工介入 |
| 测试失败 | 分析原因并修复 | 2次 | 人工介入 |
| 阶段产出低置信度 / 偏离 `scope.md` | 返回上一阶段澄清或重做 | 1次 | **立即人工介入**，不盲目继续（对应设计哲学"回退与人工介入"） |
| **CI 流水线失败** | 分诊后自动派 Agent 修复并开 PR | 1次/分支 | 开 `ci-escalation` issue 转人工 |

### 阶段6：CI 失败自动修复（CI 侧闭环）

本阶段不在对话内执行，而由 CI 触发，是"本地阶段0-5"之外的第二道自动化回路。

| 组件 | 位置 | 职责 |
|------|------|------|
| 分诊器 | `scripts/ci_failure_triage.py` | 解析 junit/coverage，输出结构化派单目标 |
| 编排工作流 | `.github/workflows/ci-autofix.yml` | 失败触发 → 分诊 → 派 Agent → 复跑验证 → 开 PR |
| 单测 | `scripts/test_ci_failure_triage.py` | 分诊逻辑离线单测（8 例） |
| 漂移自检 | `scripts/check_workflow_drift.py` | 校验本文档与实际代码/工作流是否一致，漂移即标红（对应文章 22 防线三） |

> **文档不漂移保证**：本文档描述的阶段映射、阈值（`COVERAGE_GATE = 60`、
> `MAX_FIX_TARGETS = 5`）、脚本引用，由 `ci-tests.yml` 的 `workflow-drift` job
> 自动校验。真相源以代码为准；改代码后未同步本文档会导致 CI 标红。

**分诊分类 → 派单映射**：

| kind | 触发条件 | 派发 Agent | 处理方式 |
|------|---------|-----------|---------|
| `test_failure` | junit 存在 failure/error | python-coder | 修实现优先，用例明显过时才改用例 |
| `coverage_gate` | 总体覆盖率 < 60% | test-generator | 定位覆盖率最低且语句数≥10 的文件补测 |
| `missing_report` | junit 报告缺失 | 人工 | 收集阶段就失败，不做猜测性修复 |

**安全约束（不可放宽）**：
- 修复结果一律走 PR，**绝不直推分支**；未通过本地复跑的 PR 打 `needs-human` 标签
- Agent 禁止改 `.github/`、依赖版本、`.env`、部署配置
- **阶段6 自动修复禁止改已有测试的断言来消红**：确需改测试须输出变更申请（声明类别：需求变更/契约变更/测试自身 bug，附可追溯依据）走人审；实现修复与测试调整须分成两个 PR（已有测试是验收标准，动了就没有裁判）。说不出依据的改测试直接拒绝（对应文章 23 第三问兑换法则）
- 单次派单目标上限 `MAX_FIX_TARGETS=5`，控制改动面
- 同一 base 分支已有开放的 `auto-fix/ci-*` PR 时跳过，避免刷 PR

### 智能决策减少中断

**可自动决策（不中断流程）**：
- 代码风格不一致 → 自动格式化
- 非核心依赖版本差异 → 优先沿用 lockfile（如 `uv.lock`/`Cargo.lock`）锁定的版本或用户显式指定版本，不盲目追新
- 测试覆盖率略低（核心逻辑已覆盖）→ 记录技术债务
- 补丁级技术选型冲突 → 选择团队最熟悉方案

**必须人工介入**：
- 架构设计重大变更
- 安全漏洞无法自动修复
- 业务流程与需求不符
- 同一问题循环修复超过3次

### 中断率目标
- 简单功能（CRUD）：中断率 < 5%
- 中等复杂度：中断率 < 15%
- 高复杂度：中断率 < 30%

### 可选高级手段：多路径投票（Mixture of Agents）

> 对应设计哲学"多路径投票"机制。仅用于**高不确定 / 高风险**任务（如核心算法选型、架构方案权衡）。

- **做法**：对同一子任务并行跑 2~3 条不同推理链（不同 prompt phrasing 或不同 agent），用独立评审挑优或合并结果。
- **代价**：约 2~3 倍计算/调用成本，仅在偏差代价高于成本时启用。
- **不突破限制**：仍是降低方差、不消除方差；最终仍由人裁定。

## 最佳实践

1. **文档驱动**：每个阶段的输出文档是下一阶段的输入
2. **质量门禁**：审查阶段作为质量门禁，阻塞问题必须修复
3. **快速反馈**：发现问题尽快反馈给上游Agent
4. **可追溯性**：保留各阶段的输出，便于问题追溯
5. **并行执行**：前后端编码、数据库和API设计可以并行进行
6. **迭代优化**：复杂功能可以分多轮迭代完成
7. **预防为主**：前置检查减少流程中断
8. **自动修复**：常见问题自动修复，减少人工介入
9. **按需选择**：根据项目复杂度选择必要的Agent，避免过度设计
10. **持续改进**：基于执行反馈优化Agent协作流程
11. **按需扩展**：根据项目需求选择基础或完整工作流
